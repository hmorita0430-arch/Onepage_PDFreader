## 1. 目的

手製の電子書籍(見開き2ページを1枚の写真として取り込んだPDF)を、AndroidとWindowsで **1ページずつ、適度な拡大で** 快適に読めるリーダーを作る。

## 2. 前提(事実)

| 項目 | 内容 |
|---|---|
| 入力 | 見開き1枚の写真が、PDFの1ページ分になっている |
| 規模 | 1冊100〜300ページ、30〜60MB程度 |
| PDFの中身 | 画像が主体。OCRの文字データが入る場合もある。本アプリは文字データの有無に依存しない |
| 見開き以外の画像 | 先頭(表紙)以外にはほぼない。撮影ごとの分割位置のずれもほぼない(利用者の見込み。サンプルで未確認) |
| 保存場所 | Googleドライブ |
| 利用者 | 自分専用 |
| 対象端末 | Android、Windows |

## 3. 機能要件

### 3.1 表示

| ID | 要件 |
|---|---|
| D-1 | 見開き画像を、表示上のみ左右に分割する(PDF自体は加工しない) |
| D-2 | 分割位置は画像の中心を基本とし、手動で調整できる。設定は本ごとに保存 |
| D-3 | 開き方向(右開き/左開き)を本ごとに設定できる |
| D-4 | 1ページを画面にフィット(ページ全体)して表示する |
| D-5 | 余白は本ごとの共通枠を手動で設定してトリミングし、ページ単位で微調整できる。余白の自動検出は対象外 |
| D-6 | 縦長画面は1ページ表示。横長画面は設定で1ページ/2ページを選べる。2ページ表示では、撮影した見開き1枚の左右をそのまま並べる |
| D-7 | 本ごとに、開始ページのずれ(例: 1枚目は片側のみ=表紙)と、印刷ページ番号との対応(例: 通し番号8=印刷p.1)を設定できる |
| D-8 | ピンチ、ダブルタップ、マウスホイールで手動ズームできる |
| D-9 | ページを送るたびにフィット表示へ戻る。ただし「ズーム維持」モードでは、倍率と表示位置を次のページへ引き継ぐ。表示位置は画面座標ではなく、トリミング後のページ内での相対位置で引き継ぐ |

### 3.2 操作

| ID | 要件 |
|---|---|
| O-1 | 画面の**上部の帯(上約20%・全幅)**をタップでメニュー表示/非表示(左上・右上でもページ送りにならない)。その下の左右の端25%ずつをタップでページ送り、中央をタップでメニュー表示/非表示。ズーム中も同じ。ダブルタップでの拡大は、帯の下の中央のみ |
| O-2 | 左右どちらが「次」になるかは、開き方向の設定に連動する |
| O-3 | スワイプ、キーボードの矢印キーでもページ送りできる。ただしズーム中(ズーム維持モードを含む)のスワイプは表示位置の移動だけとし、ページ送りは端のタップとキー操作で行う |
| O-4 | 注釈ツールの使用中は、タップによるページ送りを無効にする |

### 3.3 ナビゲーション

| ID | 要件 |
|---|---|
| N-1 | 最後に読んだ位置を自動で記憶し、次回そこから開く |
| N-2 | ページジャンプ |
| N-3 | サムネイル一覧 |
| N-4 | 名前つきページ: しおりと目次を1つの仕組みで登録する(例: 「第3章=45ページ」)。種類(しおり/目次)で表示を分け、どちらも複数登録できる。PDF内の目次データの読み込みは対象外 |

### 3.4 注釈

| ID | 要件 |
|---|---|
| A-1 | 蛍光ペン: 矩形指定と自由線をツールバーで切り替える。色は数色から選択 |
| A-2 | 位置つきメモ: ページ上の任意の位置に貼り、タップで文章を開く(メモと付箋は区別しない) |
| A-3 | 注釈はPDF本体を書き換えず、別データとして保存する。座標は元画像基準の正規化座標で持ち、ページとの紐づけは4章に従う |
| A-4 | 出力はMarkdown(ページ番号+メモ内容)と注釈を重ねた画像を併用する。ページ番号は印刷番号と通し番号を併記する(例: p.45(通し番号52)) |
| A-5 | 出力はいつでも実行でき、ドライブの通常フォルダに保存する。既定はマイドライブ/読書ノート/本の名前/。設定で、ドライブ上の別のフォルダを書き出し先に選べる(アプリ全体で1つ。この端末内に保存)。フォルダは初回に自動作成する |

### 3.5 Googleドライブ連携・保存

| ID | 要件 |
|---|---|
| G-1 | PDFは、Googleの標準ピッカーで1冊ずつ選んで開く。本棚機能は持たない |
| G-2 | 最後に読んだ位置・名前つきページ・注釈・本ごとの設定は、AndroidとWindowsの間で同期する(ドライブのアプリ専用領域に保存) |
| G-3 | ドライブへの接続が切れても、読書と端末内での注釈は続けられる。同期と出力は保留し、「再接続」ボタン1回で再開する。未同期の件数を画面に常に表示する |
| G-4 | 開いた本は自動で端末に保存し、次回からオフラインで読める。保存済みの本の一覧・使用容量の表示・削除ができる。保存時にブラウザへ永続化を要求する。端末から本を削除しても、注釈などの同期データはドライブに残る |
| G-5 | 同期データの形式は、第1段階から同期を前提に設計する(4章) |

## 4. データ設計の原則

注釈は「PDFのページ番号+左右」に紐づけ、設定を変えてもずれないようにする。この章は第1段階で確定し、後から変えない。

| 原則 | 内容 |
|---|---|
| 保存先の分離 | 同期データ(最後に読んだ位置・名前つきページ・注釈・本ごとの設定)はアプリ専用領域。人が読む出力は通常フォルダ |
| ページの識別 | 物理位置(PDFのページ番号+左/右)で持つ。論理ページ・通し番号・印刷番号は、表示や出力のたびに本の設定から計算する |
| 座標 | 元画像基準の正規化座標(0〜1)。分割位置やトリミングを変えても影響しない |
| 本の識別 | GoogleドライブのファイルID。同じ本を入れ直した場合は別の本として扱い、引き継ぎは対象外 |
| ページ単位の上書き欄 | 「このページは分割しない」「このページだけ分割位置を変える」を入れられる欄を、データ形式にだけ用意する(画面は作らない) |
| 注釈の同期 | 注釈1件ごとにIDと更新日時を持たせて統合する。両端末の注釈は両方残し、同じ注釈を両方で編集した場合は新しい方を採用。削除は「削除済み」の印を残して他端末に伝える |
| その他の同期 | 名前つきページは注釈と同じ規則。最後に読んだ位置は日時が新しい方。本ごとの設定は項目ごとに新しい方 |
| 読書の記録(第5回で追加) | 読み始めた日・読了日を、本ごとの同期データに追加(省略可の項目 `reading`。形式の版は変えない)。読み始めた日は、初めて開いた日が自動で入り、別々の端末で初めて開いた場合は早い日付、手で直した値は自動より優先。読了日は、最終ページでの確認(はい)または手入力のときだけ記録し、新しい操作が優先(消した操作も伝わる) |
| 文字データ | 有無に依存しない。将来の検索やAI復習向けの出力で使える余地は残す |

## 5. 非機能要件・方針

サーバーを持たないPWAとし、ドライブへの接続が約1時間で切れる前提で設計する。

| 項目 | 内容 |
|---|---|
| 形態 | PWA(Webアプリ)。AndroidとWindowsの両方で動作 |
| 公開 | GitHub Pages(コードのみ公開) |
| 認証方式 | Google Identity Servicesのトークン方式。リフレッシュトークンは使わない。アクセストークンは約1時間で切れ、再取得には利用者の操作が必要(G-3で対応) |
| 公開ステータス | Google側はTestingのまま固定し、自分だけをテストユーザーに登録する。約7日ごとの再同意が必要になる可能性は受け入れる |
| 権限(スコープ) | `drive.file`(ピッカーで選んだPDFの読み取り、出力フォルダへの書き込み)と `drive.appdata`(同期データ)に限る |
| 秘密情報 | クライアントシークレットは持たない。PDF・注釈・出力は.gitignoreで除外する |
| APIキー | ピッカー用のAPIキーは公開される前提で、使えるサイト(リファラー)と使えるAPIを制限する。承認済みのJavaScript生成元はGitHub Pagesとlocalhostに限る |
| 性能(表示) | 表示中のページと前後のページのみを描画し、大きなPDFでも軽快に動作させる |
| 性能(初回取得) | 初回の30〜60MBのダウンロードでは進捗を表示し、中断しても再開できる |
| 対象ブラウザ | Android版Chrome、Windows版Edge/Chrome |
| 画面の言語 | 日本語のみ |
| 範囲外 | 夜間モード、明るさ調整、反転表示、余白の自動検出、文字単位の選択、撮影画像の傾き・歪みの補正(取り込み側で行う) |

## 6. 開発の段階と受け入れ基準

第1段階で「読めること」と「4章のデータ形式」を確定し、同期・注釈は後の段階に積む。

| 段階 | 内容 | 受け入れ基準 |
|---|---|---|
| 第1段階 | ドライブから開く、左右分割、1ページずつフィット表示、ページ送り、接続切れ時の再接続、4章のデータ形式の確定 | 実際の本1冊をAndroidとWindowsで開き、最後までページ送りできる。接続が切れた後も読書を続けられる |
| 第2段階 | ズーム(ズーム維持モードを含む)、余白の手動トリミング、横長画面の1ページ/2ページ切り替え、オフライン保存、最後に読んだ位置の記憶 | 機内モードで保存済みの本を読める。ズーム維持モードでページを送っても、同じ倍率・同じ相対位置が表示される |
| 第3段階 | 端末間の同期、サムネイル、名前つきページ(しおり・目次)、ページジャンプ | 片方の端末で付けたしおりがもう片方に反映される。両方をオフラインで編集してから同期しても、どちらの登録も消えない |
| 第4段階 | 位置つきメモ、蛍光ペン、出力(Markdown+画像) | 出力フォルダにMarkdownと注釈入り画像ができ、ドライブ上で開ける。分割位置を変えても注釈の位置がずれない |

## 7. 事実と留意点、リスク

最大のリスクは、再接続の手間で同期が保留されたままになり、端末間で内容がずれること。

### 事実(公式資料などで確認済み)

- サーバーを持たないブラウザのみのアプリ(トークン方式)では、リフレッシュトークンが発行されない。期限切れ後の再取得には、ボタン操作など利用者の操作が必要([Google: Choose a user authorization model](https://developers.google.cn/identity/oauth2/web/guides/choose-authorization-model?hl=en))
- 期限切れのアクセストークンを自動で更新する機能は、セキュリティのため廃止されている([Google: Authorizing for Web](https://developers.google.cn/identity/oauth2/web/guides/overview?hl=en))
- アプリ専用領域(appDataFolder)はそのアプリだけが使え、利用者にも他のアプリにも見えない。ドライブの画面からも開けない([Google: Store application-specific data](https://developers.google.com/workspace/drive/api/guides/appdata))
- `drive.appdata` は機密情報を含まないスコープに分類されている([Google: アプリ固有のデータを保存する](https://developers.google.com/workspace/drive/api/guides/appdata?hl=ja))
- ブラウザのオフライン保存領域は端末の空き容量に依存し、上限に近づくとブラウザが自動で削除する場合がある
- 文字データのない画像のページでは、文字単位の選択はできない

### 未確認の前提

- Testingでは、テストユーザーの許可が7日で切れるという説明がある。確認できたのはリフレッシュトークンの例だけで([Google Ads API Forum](https://groups.google.com/g/AdWords-API/c/vaYQH19Wvm8))、トークン方式でも再同意が必要になるかは実機で確かめる

### リスクと対策

| リスク | 起きる流れ | 深刻度 | 対策 |
|---|---|---|---|
| 再接続の手間 | 1時間ごとの再接続と約7日ごとの再同意が重なる → 同期が保留のまま → 端末間で内容がずれる | 高 | 未同期の件数を常に表示する(G-3)。実機で2週間使い、手間が大きければ公開ステータスを見直す |
| 同期で注釈が消える | 統合の不具合で1回でも消える → 信頼を失う | 高 | 4章の統合規則を第3段階の受け入れ基準で検証する |
| 撮影ごとのずれ | 「見開き以外の画像はほぼない」という見込みが外れる → ページごとの手作業が増える | 中 | データ形式に上書き欄だけ用意する(4章)。サンプルで確認する |
| 範囲の拡大 | 複数のしおり・ズーム維持が加わった → 第2・第3段階で止まりやすい | 中 | 各段階で「これがないと読めない」ものだけを残す |
